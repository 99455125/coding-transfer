## 排查「只差换行符的文件被判为变更」

- 结论：核心层是字节级比较，天然把 CRLF/LF 差异判为变更，这不是 bug。
  - `SafeFiles.scan` 逐文件 `readAllBytes`；`SyncEngine.diff` 用 `Arrays.equals`；`Model.hash` 是原始字节 SHA-256；`Codec.validate` 还要求 `before != after`。
  - 传输链路（Codec → GZIP+Base64 剪贴板 / TextPatch）不改字节：TextPatch 把 `\r` 留在行内容里，往返 CRLF 不变；README 也明确「不做文本/换行转换」。
  - VM 侧发送列表来自 Git 视图（`GitHistory.workingChanges` = `git diff --name-status HEAD` + `ls-files --others`），与字节级 payload 可能不一致（列表是 Git 过滤后的视角）。
  - `SyncPanel.generate/receive/apply` 都会先 `FileDocumentManager.saveAllDocuments()`，IDE 的换行符设置/`.editorconfig` 可能在这一步把磁盘文件写成另一种换行符。
- 复现手段（可复用）：core 包无 IDEA 依赖，可单独编译后用探针跑
  - `/Applications/IntelliJ IDEA.app/Contents/jbr/Contents/Home/bin/javac -d classes $(find src/main/java/dev/codingtransfer/core -name '*.java') EolProbe.java`
  - 注意 `SafeFiles.noLinks` 拒绝符号链接，临时目录必须用 `/private/tmp`，不能用 `/tmp`（/tmp→/private/tmp）。
  - 探针结果：干净同步后 changes=0；对端文件被改成 LF 后 → 1 条 M（before/after SHA-256 不同，PATCH 编码）；应用后对端 Git 显示 `M` + numstat 5/5（即 IntelliJ 的「仅换行符差异」）；内容会收敛但 Git 工作区保持 modified。
- 环境事实：本机 git 全局 `core.autocrlf=input`；`* text=auto` 检出不会把 CRLF blob 改成 LF；autocrlf=input/true 也不会让字节相同的文件显示为 M（已验证）。

## 设计结论（未实施，待用户决定）

- 用户提议：同步时增加"目标端换行符 CRLF/LF"选项。**我的建议是不做**（至少不作为首选）：
  - 插件按设计是字节精确（README 第 22 行），基线/补丁/回滚/备份全依赖字节一致（`before` 哈希、`BASE_CONTENT_MISMATCH`、`STALE_PREVIEW`）；归一化写入等于推翻这套模型，且属于协议级改动（Codec、policy hash、基线兼容、patch 校验），旧基线要重新全量同步。
  - 归一化会改写业务仓库的真实字节：VM 侧工作区被写成 LF，下次 Git 检出（autocrlf=true）又变回 CRLF → 来回震荡，还可能被误提交。比现状更危险。
  - 根因在仓库配置（无 `.gitattributes`、两端 autocrlf 行为不一致），不在插件。
- 建议路线：①VM 侧 `.gitattributes`（`* text=auto eol=lf`）+ `git add --renormalize .` + 提交 + 强制重新检出 + `core.autocrlf=input`，让工作区字节 == blob 字节；②约定 HOST 内层仓库不做 checkout/切分支/回滚/stash；③插件侧只做"仅换行符差异"标注/统计（不改字节语义）——此项已多次向用户提议，尚未实施。
## 量化预测：把 HOST 改成 CRLF 检出会怎样（探针 `EolForecast.java`，只读）

- 用户修正提议：不是改 VM，而是**改 HOST 端全部按 CRLF 检出**，与 VM 一致。

- 探针模型：`autocrlf=true` 检出后工作区字节 = `toCrlf(blob)`（git smudge LF→CRLF；CRLF blob 保持不变）。
  **模型自检 2143/2144 一致（99.95%）** → 模型成立。
- 换行分布（只统计基线存在的路径，共 2358）：
  - 基线 `{CRLF=2300, LF=1, MIXED=40(二进制), NONE=17}`
  - 当前 HOST `{CRLF=2213, LF=88, MIXED=40, NONE=17}`
  - 预测 `{CRLF=2300, LF=1, MIXED=40, NONE=17}` —— **与基线完全一致**
- 结论：72 条仅换行幻影 → **0**，新增幻影 **0**。88 个 LF 文件的账正好对上：72 仅换行 + 16 内容漂移 = 88。
- 但**必须知道的坑**：那 16 个内容漂移文件 == 内层仓库 `git status` 的 16 条 `M`（= VM 未提交改动在 HOST 的映像）。`git checkout -f` / `reset --hard` 会静默用 blob 覆盖它们且无备份。
- 插件行为佐证：`GitHistory.command()`（第 23 行）固定了 hooksPath/fsmonitor/splitIndex/sparseCheckout/gc/maintenance/protocol，**故意不设 `core.autocrlf`**；`init()` 只在需要时加 `--object-format=sha256`，不写 autocrlf，且 `git init` 对已存在仓库不重置已有配置 → 仓库本地 `core.autocrlf=true` 能跨同步存活。HOST 侧不能用 `.gitattributes`（会变成未跟踪文件被插件当变更发走）。
- 已实测（scratch repo，未碰业务仓库）：`git config core.autocrlf true` + `git checkout-index -f -- <path>` 能把漂移成 LF 的工作区重新物化成 CRLF，且 `git status` 干净。
- 残余风险：VM 侧现在 `w/lf` 有 82 个，而基线里 LF 只有 1 个 → VM 也漂移了（很可能是之前 HOST→VM 发送时把 LF 带过去的）。只改 HOST 只堵源头，下次同步这 82 个会反向变成幻影。

## HOST 改 CRLF 对「日常使用/阅读」的影响面（实测核对，未改动仓库）

- 现场事实（`git ls-files` + 目录检查）：
  - 仓库里**没有** `*.sh` / `*.bash` / `*.zsh` / `*.cmd` / `*.bat` / `*.ps1`，也没有 `mvnw` / `gradlew` → macOS 上不存在 CRLF 破坏 shebang（bad interpreter）的风险。
  - 只有顶层一个 `Dockerfile`，且它**现在已经是 CRLF**（`i/lf w/crlf`）且不在幻影列表里 → 改配置不会让它变差。
  - 无 `.editorconfig`、无 `.gitattributes`、无 `.git/info/attributes` → `core.autocrlf` 是唯一可用的杠杆。
  - 工作区根 `~/IdeaProjects/shie-agent-dev` 有 `.idea`，**映射目录 `shie-ri-core` 内也有 `.idea`** → 该目录确实被 IDEA 打开过（`.idea/**` 在 exclude 里，不会被同步，所以 IDEA 工程文件不会产生幻影）。
- 不受影响：编辑器阅读/跳转/搜索（IDEA、VS Code 对 CRLF 透明，只在状态栏显示 CRLF）；`git diff` / `git status` / `git grep`（Git 内部归一化）；Maven 编译（javac 接受 CRLF）；插件本身的字节比较与传输；VM 侧（配置只写在 HOST 内层仓库本地）。
- 需要注意（真实风险）：
  1. **在 HOST 上编辑镜像目录里的文件并保存**：IDE 按自己的行分隔符设置写盘，macOS 上若为 LF 就会把文件写回 LF → 幻影重现。这是唯一实质风险。`shie-ri-core/.idea` 存在说明确实可能发生。防线：IDEA 的 `Settings → Editor → Code Style → Line separator` 设为 CRLF，或约定 HOST 侧只读（编辑都在 VM 上做）。
  2. 命令行按行处理：CRLF 下 `grep 'x$'` 匹配不到（行尾多一个 `\r`），`awk '{print $NF}'` 末字段带 `\r`；`ripgrep` 识别 CRLF 不受影响，Python `open()` 的 universal newlines 不受影响，`wc -l` 不受影响。
  3. **重新物化后要重新点一次预览**：`GitHistory.state()` 的 fingerprint 含 `.git/index` 原始字节，物化会刷新 index 的 stat 缓存 → 插件的 `STALE_PREVIEW` 检查会判"Git HEAD/refs/index 被外部修改"。这是既有行为，不是新增缺陷。
  4. 别在 IDEA 的 Git 工具窗口里对镜像仓库做 checkout/rollback —— 那正是 09-20 那 72 条的来源。
- 插件侧不需要改：`GitHistory.command()` 固定了一堆配置但没碰 `core.autocrlf`，设置不会被插件重置。
- 顺带：`SyncPanel.content()` 用 `TextPatch.text(bytes)` 原样展示（保留 `\r`），交给 IDEA 的 diff 引擎比较；IDEA 的 diff 会归一化行分隔符，所以只会显示「仅换行符差异」提示，不会把每行都标成改动。
- 若以后仓库里出现需要在 macOS 执行的脚本，正确做法是在 **`.git/info/attributes`**（不在工作区，插件看不见，不会被当变更发走）里加 `*.sh text eol=lf` 之类例外，而**不是**在工作区放 `.gitattributes`。现在不要加：`Dockerfile` 在两端都是 CRLF，加了反而制造新幻影。

### `applyLocked` 的回滚语义（源码确认，三个状态）

`backups/<uuid>/status.txt` 只有三种取值：
- `PREPARED`（第 133 行，首次业务文件写入前落盘）→ 进程被杀/中断 → 工作区**半写**，既没完成也没回滚。
- `APPLIED`（第 163 行）→ 全部写入并校验 → 工作区是**新内容**。
- `APPLY_FAILED\n<failure>\nRollback: restored` 或 `... Rollback: 部分文件需要人工恢复: ...`（第 159 行）→ 干净回滚 / 部分回滚失败（`回滚时文件被外部修改: <path>`）。

**插件自己的回滚把每个已写文件恢复成 `c.before()`（= 接收端自己的 apply 前字节）→ 干净回滚不可能造成 `BASE_CONTENT_MISMATCH`。** 能造成的是 `PREPARED` 和部分回滚。

**Git 层面的回滚（`git checkout --` / `restore` / `reset --hard`）才是常见元凶**：它恢复的是**已提交 blob**，不是插件基线——(1) 基线是**工作区**快照，含接收端未提交改动，git 回滚会静默丢弃；(2) 检出写的是 blob（LF），只要 `core.autocrlf` 不是 `true`（用户正打算改 `input`！）就会把文件变成 **LF**，而基线是 CRLF → 立刻 mismatch。

| 版本 | sha256 | 字节 | 换行 |
|---|---|---|---|
| VM 基线（VM 必须具备） | `ef8bd550550d…` | 3461 | 纯 CRLF |
| HOST 当前（要发出去的） | `95e52fc6588b…` | 3565 | **CRLF+LF 混合** |

## 设计质疑的答复：VM 接收端到底校验了什么（14:0x）

用户问题：git rollback 未提交的工作区是日常操作，为什么会让同步失败？并提出三条改法：
(a) VM 接收时不校验基线；(b) 不要改基线；(c) 增量同步就按 VM 发送的基线来。

**先纠正前提（读源码得到，SKILL.md 已补入）**：VM 接收时**不读任何本地基线文件**。
`SyncEngine.preview` 在 VM 侧只有两个校验，都是拿 **VM 的实时状态**去比：

| 校验 | 位置 | 比较对象 | 报错 |
|---|---|---|---|
| `checkHead` | L74 → L94-96 | VM 当前 HEAD vs `payload.head()`（HOST 基线记录的 head） | `BASE_MISMATCH` |
| 逐条 `before` | L75, L81 | `SafeFiles.scan(root)`（VM 实时工作区） vs `entry.before()`（HOST 对 VM 的认知） | `BASE_CONTENT_MISMATCH` |

唯一在用的 `.vmsync/baselines/<id>.gz` 是 **HOST 侧**那份（`generate` L53 拿它 diff HOST 工作区）。
所以 (a) 的实质是"不再校验 VM 自己的当前字节"，是撤掉安全网，不是去掉记账步骤。

**`before` 校验为什么是安全前提**：`applyLocked` L142-144 在每次写前又断言一次
`Arrays.equals(now, c.before())`（否则 `STALE_PREVIEW`）。HOST 的 `after` 是**整文件替换**，
不证明被替换的是什么就写，等于静默摧毁 VM 对该路径的其他改动；而且 `PATCH` 的
`TextPatch.apply(old, data)` 本身就要 `old` 才能重建 `new`。去掉校验 → 文本条目只能退回 `RAW`
（整文件下发），**更不安全**。诚实的边界：它证明的是字节而非意图，VM 侧"回退到恰好等于基线"
的改动会被静默放行。

**(b) 不改基线不行**：HOST 的发送清单就是 `diff(baseline, hostWorktree)`，基线不动 → 每轮重复
发送同一批文件，且永远学不到 VM 的新状态。

**(c) "增量按 VM 发送的基线来" 其实就是现状**：Bundle 路径 `BundleSync.target` L55 要求
`baseline.git().snapshot().equals(payload.git().parent())`，而 `parent` 来自 VM 的
`acknowledged`（`generate` L37）——基线 id 本来就是 VM 发出来的。

**结论**：失败原因不是"基线被动过"，而是 **VM 工作区字节变了**（git rollback 恢复 blob=LF，
基线=CRLF）。`base == toCrlf(blob)` 成立 → 只有 VM 的 `core.autocrlf=true` 时 rollback 才字节安全。

### 编码开销实测（EncCompare.java，已收入 skill scripts/）

16 条目真实发送，chunkKb=2048：entry data 3,848,861(PATCH) vs 1,893,233(RAW) = -50.8%；
`Codec.encode` 509,577 vs 258,566 = -49.3%；clipboard chars 679,775 vs 345,095 = -49.2%；
**chunk 数都是 1** → PATCH 的 ~2x 开销今天不额外增加复制/粘贴次数，只在逼近 4 MiB 上限时才成为真成本。

### 给用户的三个选项（未执行，等选择）

A. 零改动：VM 侧 `core.autocrlf=true`（或 `core.eol=crlf`）后再 rollback，检出会补回 CRLF 正好等于基线；
B. 插件加显式"覆盖 VM 本地改动"强制开关（接收端复选框，列出受影响文件后跳过 `before` 校验）——保留默认安全 + 给出逃生口；
C. 扫描时统一换行（内存规范 LF，写回按文件恢复原 EOL）——改动最大，动到字节精确契约。

### 关键技术结论（本轮新发现，有实测支撑）

1. **PATCH 编码是纯冗余，可以整体删除。** 两条独立证据：
   - 体积：`TextPatch.create` 同时写入**完整旧文 + 完整新文**，所以条目数据 ≈ 2× 原文。
     实测 16 条目：entry data 3,848,861(PATCH) vs 1,893,233(RAW) = **−50.8%**；
     `Codec.encode` 后 509,577 vs 258,566 = **−49.3%**；两者块数都是 1。
   - 安全性：它想提供的「旧文一致」检查，**`before` 哈希本来就随每个条目发送**，且
     `SyncEngine.preview` L81 / `BundleSync.target` L58 **无条件**校验（与编码无关）。
     `TextPatch.apply` 再验一遍 = 同一个断言。
   - 关键性质：**RAW 是既有编码，老接收端照常接受 → 这是协议兼容的简化，不是破坏性变更。**
     `TextPatch.text()` 仍需保留（UI diff 与 UTF-8 判定用）。
2. **全内存模型是扩展性天花板**：`Codec.encode` 的峰值 ≈ 包体 ×3~4
   （raw BAOS + gzip BAOS + Base64 String + 分块 List<String>）。建议流式编码。
   对比参照：`FileTransfer` 已经是落盘快照 + `RandomAccessFile` 惰性读块，是项目传输该学的样板。
3. **`chunkKb` 上限 4096 KiB 正好等于 4 MiB 单块上限**，再调大只会被 `parse` 拒绝。
4. 一处易错点：项目包的 `chunkKb` 作用在 **Base64 字符串**宽度上，文件包作用在
   **原始字节**宽度（`chunkKb*1024/4*3`）——两者最终等效但实现路径不同。
5. 一次 apply 会把项目**完整读 4 遍**（preview scan、applyLocked 的 before-same、after-same、
   checkHead 各一轮）。
6. `hash(null) == "-"` 导致「接收方文件不存在」也报 `BASE_CONTENT_MISMATCH: VM 文件已有不同修改`
   → 排查误导，建议区分 ABSENT / MODIFIED。
7. `SafeFiles.state()` 每次调用都读+写 `.vmsync/.gitignore`，而它被 `baseline()` 等高频路径调用。

### 优化优先级建议（已写入文档 §11）

★★★ 删 PATCH（协议兼容、收益最大） → ★★★ 流式编码 → ★★ 降低人工复制成本 /
接收端「覆盖本地改动」显式开关 → ★★ 一键回滚（`backups/` 数据已齐全，只缺 UI 入口）→
★ index 假阳性（需用户同意，AGENTS.md 禁止自动 reset/add）→ ★ 报错区分度 → ★ 性能微调。
